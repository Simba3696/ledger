# ADR-0008: Sync GitHub storage through per-device op logs joined into registers

**Status:** Accepted (2026-10-10). Amends [ADR-0007](0007-serverless-github-storage-mode.md)'s storage layout and the epic's T5, #8 and #9. ADR-0007 itself is unchanged.

## Context
ADR-0007 stores a household's data as one shared `ledger.json.enc`. The first sync engine for it (#7) merged each device's copy three ways against a remembered base and wrote it back with a sha-guarded PUT. Building it surfaced 28 data-loss or correctness bugs (B1-B28 in the #7 spec). 20 of the 28 came from four sources: the shared file, the remembered base going stale when a PUT's response is lost, replaying in-flight edits, and treating timestamps as intent. Each fix added state, and that state opened the next hole. That branch was not merged.

The redesign (the spec in #7, accepted by the owner on 2026-10-10) removes those four sources rather than adding rules around them. GitHub mode is unreleased, so there is nothing to migrate.

Issue #10 had reserved ADR-0008 for its sign-in helper. This decision takes 0008, and #10 takes the next free number.

## Decision
These deviations from ADR-0007, the epic and its children (the spec's Appendix A) apply:
1. **Files.** The shared `ledger.json.enc` becomes one `genesis` per epoch plus per-device `log` and `snap` files, all in one `ledger/` folder: `<epochKey>.genesis.enc` and `<epochKey>.<deviceId>.<log|snap>.enc`. A device writes only its own files and a genesis it creates. Nothing is ever deleted. Every file uses ADR-0007's encryption format unchanged.
2. **Merge.** The three-way merge against a base, with a blocking prompt, becomes a join of registers. Every document part is a register `{value, tag}`, and the tag is `[Lamport L, deviceId]`. A join keeps the register with the greater tag, so conflicts resolve the same way on every device without blocking. The losing device gets a notice afterwards. The `conflict` status is removed.
3. **Deletes.** 90-day tombstones keyed by `deletedAt` become a deleted set that only grows during an epoch, and delete wins over a concurrent edit (remove-wins). The rule that a later `updatedAt` survives a tombstone and the restore re-stamp rule are removed. Wall-clock time orders nothing.
4. **Retry.** The sha-guarded retry on the shared file becomes a sha-guarded retry on the device's own file, still at most 4 PUTs a cycle.
5. **Restore (#9)** writes a new epoch genesis. The greatest epoch key with a listed genesis wins, and changes the restore left out are offered for re-apply. Export is the materialised document in the same encrypted format. Sync does not use the `restoredAt` marker.
6. `LedgerDocument.tombstones` stays in the type for `DocumentBackend`, and is always `[]` in GitHub mode.
7. **#8.** "Is there a ledger?" means "does a listing of `ledger/` contain a genesis?". Create is one genesis PUT.

Format details settled while building the core (stage 1):
- An equal tag can happen only after a fork. It is broken by comparing the values' canonical JSON, which is a total order with no collision risk, instead of comparing hashes of the values.
- A new list record's order key pads L to 16 digits. Every L below 2^50 has at most 16 digits, so the keys compare as strings in L order. The validator accepts only the two shapes keys.ts makes, `0.<base36 index>` and `1.<16-digit L>.<deviceId>`: any other text could sort after the next local create's key and make the diff refuse every later add to that list. This tightens the fv 1 validator, possible only before fv 1 ships.
- A create's order key must name the L of the op that sets it (`orderKeyNames`). The device part is not bound, because a rehome re-issues a create under a new device id with its original L (spec section 10.3). So re-apply (spec section 9.4) re-creates a debt, EMI or subscription with its old id but a **fresh** `_c`, `{o: createOrderKey(L, device)}` for the re-apply op's own L and the device's new id, and the record lists last, as any new create does. Records re-created in one list by the one op share that key and list by id, so re-apply appends them in id order; the diff accepts several creates in one list in that order and refuses any other. The old `_c` names an L from the old epoch, which could sort after the next local create's key in the new epoch, so the validator refuses an op carrying it, and re-apply would always fail. An expense keeps its old `{m}`, which holds no L. This amends the spec's section 9.4 ("re-created with its old id, `_c` and all current old-state fields").
- Rehome's re-issue (spec section 10.3 step 4) keeps one op per original L, but is whole where the validator needs it to be (`rehome.ts`). An op that re-issues a record's `_c` also sets every field and `_s` of that record; a field whose own tag is later or foreign gets its current value, and its own tag still decides it on join. A field group (an EMI's balance pair) is re-issued whole when either of its registers is. Re-issued per register, as the spec says, the log would be refused whenever a record created after the fork point was edited later, or two forked payments settled the same date. Re-apply markers (`ra`, spec section 9.4) are re-issued too: every marker of the pre-rehome state that the rebuilt state lacks goes on the last re-issued op, or alone on an op at the device's greatest own L. A marker has no tag, so a walk of registers and deletions alone would drop it, and a discarded or re-applied restore group would be offered again on every device. This amends the spec's section 10.3 step 4 ("every register and del"), as section 9.4 is amended above.
- Record ids are `crypto.randomUUID()` uuids. A genesis or backup must pass the deep `isWritableDocument` check, which uses the same field checks as the op validator. An expense's `sortKey` must be a key the fractional-index code (`sortKey.ts`) accepts, so no remote key can make a later append or move in its month fail. The check sets no length limit, so `keyBetween` builds a key in constant stack depth however long its neighbours are (a recursion per digit overflowed the stack on a key ending in a long run of `z`).
- The structural validator is versioned by the per-file format version `fv`. Within one `fv` it may only be loosened, never tightened.
- A restore genesis's `basedOn.seen` is the section 9.2 cut exactly as built, `R.seen ∪ {R: R.ownMaxL}`, so an entry may be 0 (a restorer that wrote no op in its epoch). A 0 entry cuts nothing, the same as an absent one. Every other version vector (`vv`, a snap's `seen`) still needs each L ≥ 1.
- A tag naming the genesis pseudo-device `g` is valid only as `[1, "g"]`. A snap holding `[L, "g"]` with any other L is malformed.
- A snap is checked against its epoch's genesis state, which a device always reads before any snap (spec section 8.3). A register a snap holds under `[1, "g"]` must be exactly the genesis's register at that key, with the same canonical value. Otherwise it would tie with the genesis's register on join, and the equal-tag value tie-break would let the snap rewrite a genesis value on every device, or add genesis-tagged keys the genesis never had. For the categories, which only a genesis sets, that change would be permanent for the epoch. This tightens the fv 1 validator, possible only before fv 1 ships.
- A snap's state is consistent with its own `seen`: every register tag `[L, d]` (other than `[1, "g"]`) and every deletion `(L, by)` has L at or below `seen[d]` (absent counts as 0). Every honest state holds this, because an op sets `seen[device]` to its L and a join takes the pointwise max. Without it a snap could carry a write tagged with another device at an L that device has not reached, and win the equal-tag value tie-break against that device's real write. It also keeps `seen` trustworthy for the gap check. This tightens the fv 1 validator, possible only before fv 1 ships.
- Every name in a snap's `joined` map must be a repo file name (`<epochKey>.genesis.enc` or `<epochKey>.<deviceId>.<log|snap>.enc`), with no folder.
- An EMI's balance, `remainingAsOf` with `asOfDate`, is written as a pair: an op that changes either sets both, so the two registers always share a tag and one op's balance wins whole. Per-field registers would otherwise merge one device's amount with another's date and count a payment twice. The validator refuses an op that sets only one of the pair and a snap that holds them under different tags. This amends the spec's section 3.2 row for `updateEmi`/`payEmi` ("changed fields"). An equal tag (a fork) is broken once per pair, on the canonical JSON of both values, so a fork can't take the amount from one op and the date from the other.
- `st/timeZone` (in an op, a snap, a genesis or a backup) must have an IANA zone name's shape: one to three `/`-separated segments, each a letter followed by letters, digits, `_`, `+` or `-` (`UTC`, `EST5EDT`, `Asia/Kolkata`, `America/Argentina/Buenos_Aires`, `Etc/GMT+5`). The check is the shape only, not "does this runtime's Intl know the zone", because zone lists differ between builds and every build must agree on validity. `DocumentBackend` works out today in UTC when Intl doesn't know a well-shaped zone, so a synced zone can't make every call that needs today fail. This tightens the fv 1 validator, possible only before fv 1 ships.
- Every stored date (`asOfDate`, `untilTarget`, `expiryAnchor`, a card bill's `dueDate`) must be a real calendar day, `YYYY-MM-DD` with year 0001-9999, the same check the user's dates already pass, instead of any `\d{4}-\d{2}-\d{2}` text. This tightens the fv 1 validator, possible only before fv 1 ships. A payment settles the due date after the stored `asOfDate`, so from an `asOfDate` late in 9999 it would land in year 10000: `payEmi` refuses that with a 400, and the document is untouched. Editing the EMI re-anchors it at today.
- A payment's new balance is held to the bound every local amount passes, at most 12 integer digits (`numeric(14,2)`). The validator takes stored money with up to 15 integer digits and either sign, and the payment computes the balance from stored values: a remote negative `emiAmount` is added back for each passed due date, and a 15-digit `remainingAsOf` can round up to 1e15. `payEmi` refuses a balance past the bound with a 400, and the document is untouched, instead of the diff refusing its own op with a 500. Editing the EMI fixes it. The validator's money check is unchanged.
- An epoch key's number is 6 digits zero-padded, or more digits with no leading zero, so every number has one spelling and `e(n+1)` always exists. Numbers compare exactly at any length. An epoch counts only if a genesis is listed for it and for every number from 1 up to it, and the winner is the greatest counted key. A restore takes the number after the winner's. Honest restores add 1 to the winner, so they always extend the run. A crafted genesis such as `e999999-ffffffff` would otherwise win, and no restore could then write a greater key; numbering past a gap is ignored instead, which also keeps one file from taking the number to a length whose file names can't be written. This amends the spec's sections 2.1 (`e` + 6-digit `n`), 9.1 (the greatest key with a listed genesis wins) and 9.2 step 4 (`n` is the highest number in the listing). Re-apply markers take the same epoch keys. This loosens the fv 1 validator.
- **Lamport exhaustion starts a new epoch.** Every L in a valid file is below 2^50, so one valid op at L 2^50 - 1, or a snap whose `seen` names it, takes a joiner's `maxL` to the top of the range, and no L is left to allocate. The snap's `maxL` rule does not prevent this. No bound on files can either: if files may carry L up to some C, a device that joined a file at C - 1 must write at C, which every other device would refuse. So `nextLamport` throws `LamportExhausted`, and the host never passes it to `DocumentBackend`. Instead it restores its current materialised document as the next epoch (section 9.2: the genesis's `basedOn` is the usual cut, the device gets a new id), where L starts again at 2, and commits the write there. The write succeeds, and other devices switch to that epoch and are offered their changes it left out, as after any restore. `testkit.ts`'s `Replica` does this as the stand-in for `SyncedHost`.
- `LedgerBackend` does not change, and `DocumentBackend`'s calls and results do not change (stage 3 adds one optional `DocumentHost` hook and an optional field on the handle it returns, below). A write that the diff can't represent as an op fails closed, with a 500 and the document untouched, instead of being dropped.

Transport details settled against the real GitHub API (stage 2, recorded in [github-api-behaviour.md](../architecture/github-api-behaviour.md)):
- **The listing reads a git tree.** A cycle's step 2 and cold start list `ledger/` with one `GET git/trees/{commitSha}?recursive=1`, keeping the blobs directly in `ledger/` (`contents.ts` `listDir`). The contents API's directory listing, which the spec names, silently returns only the first 1,000 entries by name, with no flag and no paging. A newer epoch's genesis sorts after every older epoch's files, so past 1,000 files a restore would never win and new devices would never be joined. A tree has no such cap (GitHub documents 100,000 entries, and sets `truncated` when it cuts one short), is addressed by sha so it can't be a stale view of that commit, and is still one request. A truncated listing is never read as an absence. This amends the spec's sections 6 ("one listing returns every file") and 7 step 2.
- **An empty repo is not a conflict.** On a repo with no commits, `git/*` endpoints answer 409 "Git Repository is empty.". `contents.ts` maps it to `EmptyRepoError`, and `getRef` answers `{kind: "empty"}` (no ledger yet, section 9.5), never `ShaConflictError`.
- **The ref poll is conditional, as specified.** A 304 is checked before `res.ok`, because a browser hands it to script with `ok` false. Every poll sends the same `Accept`, because the ETag varies with it. The client never sets `Cache-Control` or `Pragma`, which GitHub's CORS preflight doesn't allow. The section 7 fallback (list on every cycle) is not needed.
- **Two kinds of 409.** `ShaConflictError.reason` is `"branch-race"` for "is at <head> but expected <base>": the PUT was checked against a head that has since moved. The file's sha is usually still current, because another path moved the branch, but not always: when two PUTs to the same path race, the loser gets this same message and its sha is stale by then. That happens when an own lost or late PUT lands beside the next cycle's retry (section 12, B26), or when a forked profile writes the same own log (section 10.3). So a retry of the identical PUT is allowed, and if it then gets "does not match", the engine re-runs steps 1, 2 and 5 as section 12 requires. Anything else is `"stale-sha"`. Both stay inside section 12's retry budget.
- **The engine skips identical re-PUTs.** A PUT with the current sha and identical bytes still makes an empty commit and moves the ref, which costs every other device a listing. So a push is skipped when `gitBlobSha(text)` equals the listed own sha. `putFile` doesn't skip on its own, because it can't tell a confirmed sha from a stale one.
- **Commit messages.** `"Sync <dev8>"` and `"Snapshot <dev8>"` carry hex digits 1 to 8 of the device id (the 8 after the `d`), built by `deviceCommitMessage`. `putFile` refuses any message outside the fixed set before sending anything.
- `verifyRepo` returns the default branch, which the ref poll reads (section 7).

Local engine details settled while building the stage-3 commit path and stale-UI fence (spec sections 3.4 and 3.5):
- **A write is fenced by what was on screen when it was submitted.** `DocumentBackend` queues each write behind the ones before it, so a write is diffed later than the user pressed Save, and the view may have rendered a join in between, after the form's values were taken. Fenced by the revision rendered at diff time, as the spec says, that stale value read as a deliberate edit and set the remote change back with no notice. So `DocumentHost` gains an optional `begin()`, which `DocumentBackend` calls synchronously when a write is submitted; the write then commits through the returned `HostWrite` and calls its `end()` once settled. `SyncedHost.begin` pins the write to the revision rendered at that call, and the engine fences it and stamps its `vv` by that revision. A host without `begin()` (the parity and test hosts) behaves as before. This amends the spec's sections 3.4 ("at diff time ... `rev > renderedRevision`"), 3.5 ("needs no change to `DocumentBackend`") and 14 (`DocumentBackend.ts` "untouched"). The pin can't live in `SyncedHost` alone: nothing reaches the host between submission and the write's turn in the queue. Any later port of `DocumentBackend` to main carries `begin()` too, and a host there may ignore it.
- **One pre-image per revision, kept while a pinned write needs it.** The spec keeps the oldest pre-image since the last render and discards those at or below the rendered revision. The fence instead keeps, per register, the value each revision's join replaced, plus the seen vector at each revision, from the oldest revision a write still pinned may be fenced by. A write pinned after an earlier render then compares against the value it actually saw, not an older one. This amends the spec's section 3.4.
- **An own write clears a register's pre-images only where it now stands.** Once an own op commits and is joined, a register whose live tag is the op's own `[L, deviceId]` (with the op's value) shows the user's own value, so the fence drops its pre-images; a later stale form compares against what the user now sees. Where a remote write the op never saw carries the later tag and beat it, the remote value is still unseen, so the pre-images stay and a stale form that left the field as it was is still fenced. Clearing them for every key the op set let the next stale submit revert the unseen remote value with no notice. The spec's section 3.4 has no rule for own writes; this adds one.
- **Local writes take turns, whichever path they come by.** The spec's section 3.5 says interleaving `amend` with a `DocumentBackend` write is safe because each op is a diff against `current()` at its own call. That holds for field registers only. An own op reaches `current()` only once its transaction commits, so a write diffed while another is still saving carries a whole-unit register (`fm`, `cb`, settings, categories) or a TOGETHER group (an EMI's balance pair) as it was before the other, and wins with the later L: a write the user was told was saved is set back with no notice. So `beginWrite()` orders every local write by submission: its handle gains an optional `ready`, which settles once every write begun earlier has ended. `amend(run)` takes a handle at its call, waits for `ready`, then clones `current()`, runs `run` and commits, all at its turn; `DocumentBackend` waits for `ready` before it reads the document. Diffing a write at its turn against a newer document is not a fix: `next` was built from the older one, so its stale values would set the earlier write back anyway. `amend` is fenced by the revision on screen at its call, as a `DocumentBackend` write is. This amends the spec's section 3.5 (`SyncedHost.amend`, "needs no change to `DocumentBackend`") and, with `begin()` above, section 14.
- **Tab memory is only for a browser that refuses storage.** The spec's section 10.1 keeps the old opener's memory fallback "only when the database never opened". A full device can fail every open with QuotaExceededError, and the fallback then accepted writes into tab memory that a reload loses, against owner decision D19 (a full device refuses the write, and nothing is held only in tab memory). So only an open that fails with SecurityError or InvalidStateError (an opaque origin, blocked storage, some private windows), on every attempt, while no `ledger:sync` database is listed, falls back to memory. Any other open that keeps failing (a full quota, a lost connection, a corrupt store) is `unreadable`, and writes are refused.
- **Generations are listed, not probed, where the browser can list them.** Finding the newest generation by opening `ledger:sync:<n+1>` without a version has to create that database before the upgrade can be aborted, so on a full device the probe failed, read as "IndexedDB never opened", and hid the saved records behind a first start under a new device id. `indexedDB.databases()` (Chrome, Safari 14+, Firefox 126+) lists them without creating anything. Without it the probe stays, and a probe that fails rejects (`unreadable`); it never counts as "absent". This amends the spec's section 10.1 ("reuses `persist.ts`'s hardened opener as it stands").

Sync cycle details settled while building stage 4 (spec sections 7, 10.3, 11 and 12):
- **A head is handled only when every file in it was joined.** `lastSeenCommit` and `refEtag` are recorded only when the cycle joined every log the listing names (or knew it already). A halted stream, a gap (section 8.2), a failed read or a truncated listing leaves them as they were, so the next poll gets a 200 and lists again. Section 12 says a halted stream's sha "is retried each cycle"; with the ETag recorded, the next poll would answer 304 and nothing would list that file again until another device pushed, including after the app updates past a newer `fv`. The cost, only while a stream is halted or waiting, is a counted ref read and a listing per poll. A log that waits for its snapshot (section 8.2: the snapshot is stale or can't be read) is kept in the tab by its name and blob sha while that version is listed, so a poll checks it again without downloading it again (stage 5 review, 2026-10-12: before this, every poll also downloaded the waiting log). Within one tab a file that was refused is not read again, remembered by its name and blob sha together: the sha names its bytes for good, so a new build is what can read it differently, but whether those bytes are refused also depends on the name they are checked against (section 6: content must match its name). A byte copy of a valid log under another device's name has the original's sha; remembered by sha alone, the copy's refusal, read first because it sorts first, made every device refuse the genuine log without reading it, and devices that joined it before the copy appeared never converged with those that did not.
- **A cut listing never decides the epoch.** When the listing is truncated and the winning epoch it shows is not this device's (none at all, an older one, or a newer one), the cycle is `pending`, with nothing read or written, and the next poll lists again. A device's file sorts before its epoch's genesis, so a cut tree drops the genesis first; read as it stands, such a listing gave `missing`, and could give "stale" or "switch". This applies the stage-2 rule "a truncated listing is never read as an absence" to step 3. A cut listing that does show this device's epoch winning is used as before; a newer epoch it left out is found once a listing names it.
- **A repo file is bounded and always classified.** A listed file larger than 4 MiB (`REPO_FILE_MAX_BYTES`, about 12 times a 10-year genesis or snapshot) is refused as `malformed` without being downloaded, and so is a downloaded text past it. Decryption inflates through a budget of 32 MiB of JSON (`REPO_FILE_MAX_PLAIN_BYTES`, about 14 times a 10-year document), refusing the file once it is passed, before the rest is held: gzip inflates about 1000:1, so a 64 KB file could otherwise become 48 MB, and a 1 MB one a gigabyte, on every device that reads it. Plaintext that isn't gzip is `InvalidFileError`, so `malformed`, as is any other throw while a file is read and checked. Before this a file that decrypted but wasn't gzip threw a `TypeError` that was neither refused nor remembered: every cycle read it again and failed before step 6, so this device's own writes were never pushed while it was listed, and a genesis like it showed `pending` instead of `needsAttention`. The bounds apply to repo files only; the device's own IndexedDB records are not bounded. They are a reader's limits, so a later build may raise them within fv 1.
- **Meta gains `ownLogThrough` and `lastSentLogThrough`**, the greatest own L in the confirmed own log and in the last sent text. Section 7 step 5 settles "the last send landed" from `S == lastSentLogSha` alone, which needs to know what that text held, and the `pending` count (section 11) is the own ops above the confirmed one. This amends the section 10.1 meta list.
- **The own log text is built once per content and reused.** Every encryption takes a fresh IV, so two texts of the same ops never share a sha, and "skip an identical PUT" could never apply. Sending the same bytes again after a lost or late response makes its sha match whichever send landed (`S == lastSentLogSha`), and a cycle that finds the repo holding everything it would send sends nothing.
- **Step 5 runs before step 4, and both end in one transaction.** A fork rehomes before anything else is joined (the rehome rebuilds the state anyway); otherwise the ops read from other devices and every piece of bookkeeping (files joined, the head handled, the own log confirmed) are saved together. Ops at or below what this device already joined from a device's log are not joined again: logs are cumulative and joined whole. (Stage 5 measures this from that log's earlier version alone, never from `seen`, and leaves such an op out only when the state already holds it: see `logReach` below.)
- **The fork rule also covers an own log this device can't read** (undecryptable, malformed or a newer format) and one naming a snapshot point past its K: neither is this device's history. Rehome takes a write turn, so no write is diffed across the change of id, and its cold join falls back, for a file whose listed version can't be joined, to the version this device joined before, which still reads by its sha: nothing it had from another device is dropped. The rehome notice is stored as `{kind: "rehome", from, to}` under `rehome/<new id>`. Re-issued ops carry the rebuilt state's seen vector as `vv`. The cold join also settles which streams are halted (section 12) and whether one waits for its snapshot (section 8.2), as the cycle's step 4 would from the same listing, and the rehome replaces both with what it found. Step 4 is the only other place that clears them, and it runs only for a head not yet handled: a rehome that joined every listed file records that head as handled, so a stream that healed before the rehome stayed halted (or waiting) with nothing left to read, until another device committed or the tab reloaded.
- **A rehome counts as a join for the stale-UI fence.** The spec's section 3.4 fence learns of changes only through `join()`, but a rehome (section 10.3) replaces the state whole: registers this device wrote may now carry another tag, and the other instance's values may win. So `Fence.replace` treats a rehome that changed the document (tombstones aside) like a join that changed it: it bumps the revision and keeps the pre-image of each visible register (and whole unit) whose value the rehome changed. A form on screen before the rehome is then fenced against what it did, instead of setting it back with no notice. This amends the spec's sections 3.4 and 10.3; a port, or a later change to the fence, must keep it.
- **The epoch's genesis is read once by the cycle**, since `initialize` doesn't record its sha. A genesis newer than this build is `needsUpdate` and refuses writes with a 503, one the key can't open (wrong key, or another salt and iterations) is `needsPassphrase`, and a malformed one is `needsAttention`; each stops the cycle with nothing written.
- **PUT spacing.** Section 7's "at least 5 s between own log PUTs" applies between PUTs that landed, measured on a monotonic clock, so section 12's retries at 250, 500 and 1000 ms still happen within a cycle. The hourly cap of 120 counts every PUT request, retries and keepalive pushes included. A push that is due sooner waits on a timer, with status `saving`.
- **The keepalive push sends a text built in advance.** Encryption is asynchronous and a page may be gone before it finishes, so each committed op also builds the own log text, and `pagehide` sends that text if it is still the latest. Its send is not recorded; step 5 settles it from the listing on the next start. The size limit is checked on the PUT body as sent, at most 60 KiB (`keepaliveMaxBytes`), not on the text: the body carries the text as base64 inside JSON, about 4/3 of it, and a browser refuses a keepalive body that would pass 64 KiB in flight, so a text check let bodies of about 64 to 80 KiB go out and fail. That is about 45 KiB of text. A larger push is not sent and doesn't count against the hourly cap; the next start pushes it. A keepalive push doesn't wait out the 5 s spacing: the page is going.
- **Status precedence** (section 11 lists the statuses without an order): another tab or unreadable local state, then whatever stops the cycle (`needsToken`, `missing`, `needsPassphrase`, a genesis `needsUpdate` or `needsAttention`), then `pending` (the last cycle failed: offline, a 5xx, a rate limit, a stale listing, retries spent), then `saving` (own ops not yet confirmed, or a gap to wait out), then a halted stream (`needsUpdate` if any halted on a newer format, else `needsAttention`), then `idle`. A 404 on the ref or the listing is `missing`; a 404 on a listed blob is `pending`. An empty repo (409 "Git Repository is empty."), or a listing with no counted epoch, is `missing` (section 9.5: a ledger is a listed genesis).
- **A newer epoch halts the cycle until stage 6.** Switching to a restore's epoch (section 9.3) comes with restore. Until then a listing whose winner is newer than the device's epoch stops the cycle with `needsAttention`: nothing more is pulled from or pushed to the old epoch, and local writes are kept. (Superseded by stage 6: the device switches, below.)
- `SyncStore` gains `chainEntry(L)`, the stored chain after the own op at `L`, which the fork rule compares with an own file's `chain`.

Compaction, gap check and cold start details settled while building stage 5 (spec sections 8, 10.1 and 10.3):
- **Meta gains `ownLogK`, `lastSentLogK` and `lastSentSnapThrough`.** Section 7 step 6 pushes when "K changed", so the engine has to know the `snapThrough` of the confirmed own log, also after a lost response: `ownLogK` and `lastSentLogK` are settled by step 5 exactly as `ownLogThrough` and `lastSentLogThrough` are. Versions of the own log grow in their last L and in their `snapThrough`: a trim keeps the last L and raises `snapThrough`. So step 5's read-back takes a version as newer when either is greater, not only the last L. Comparing the last L alone misread one case as a stale listing: a trim that landed while its answer was lost, after a reload had sent the same trim again as new bytes. The device then kept sending against the old sha, and every cycle ended in 409s. `lastSentSnapThrough` is the `through` of the snap text last sent, so a listed own snap sha equal to `lastSentSnapSha` confirms K without reading a 330 KB file back. This amends the section 10.1 meta list.
- **The own snap is settled in step 5, before the own log.** Section 8.1 step 3 confirms a snapshot within the compaction step. One whose answer was lost, or that a reload sent again, is settled from the next listing instead: the listed sha it knows (nothing new), the sha it last sent (that send landed), or anything else, which is read back. A snapshot of this device's own history, whose `chain` at `through` matches the local chain, is confirmed when `through` is at or past K and is a stale listing when below it. Anything else (unreadable, past `ownMaxL`, another chain) is a fork and rehomes (section 10.3), as for the own log. Confirming sets K and drops own ops at or below it from `ownLog` in one transaction. K is persisted before any trimmed log text is built, so the own log's fork rule ("a `snapThrough` past K is not this device's history") stays exact.
- **The trim is an ordinary push.** Once K moves, step 6 is due and sends the log with `snapThrough: K`. The 5 s spacing between PUTs that landed applies to the snapshot and to the trim (section 7 step 7 says "PUT own snap, then step 6 again"), so one compaction is three PUTs at least 5 s apart: the log, the snapshot, the trim. Every snapshot PUT counts against the hourly cap, and is retried as a log PUT is (at most 4 a cycle, a branch race resent as is, a stale sha re-listed and settled).
- **A snapshot is taken between two mutations.** Its state, `seen`, `maxL`, chain head and `through` (`ownMaxL`) are read in the engine's mutation queue, so no op is half applied. Ops committed after it was taken stay in `ownLog` above K and go out with the trim. Its text is built once per snapshot point and reused for every send. It is checked against the epoch's genesis with the validator every reader runs, and against the write bounds below; one this build would refuse is never published, the reason is logged once, and the log stays uncompacted, rather than failing every cycle. Its `joined` is the device's `joined` for the epoch plus its own confirmed log version.
- **A snapshot's `through` never passes its confirmed own log's last L.** The trigger check ("only while the own log is confirmed") runs before the snapshot is taken, and the cycle awaits the log text and, after a reload, a genesis blob read in between. An own op committed in that window (or queued ahead of the snapshot's view) got an L above the confirmed log's, went into the snapshot, and left `ownLog` when K moved, so it was in no published log. Readers fetch a device's snap only when its log's `snapThrough` is past what they have seen, so until the trim landed every device that had joined the log lacked it, while a device that started cold from the snapshot had it. A device retired or closed for good inside the 5 s before its trim (status `idle`, nothing pending) left them diverged for good. The view therefore checks again, in the mutation queue, that `ownMaxL == ownLogThrough` and `ownLogK == K`; if not, no snapshot is taken this cycle (and nothing is remembered for that point), the push sends the new op, and a later cycle compacts. Section 8.1's invariant S1 then holds as the spec assumes: a snapshot's own ops are all in a published log, so a trim that never lands costs only reads.
- **A snapshot's `through` must equal its `seen` for its own device** (absent counts as 0). Every honest snapshot holds this (`through` = `ownMaxL`, which an own op sets in `seen`). The gap check (section 8.2) closes a device's gap with its snapshot's `through`, which the reader also takes as that snapshot's `seen` for its own device, so a snapshot whose two said otherwise could never close the gap it was fetched for, and a log would wait for it for good. This tightens the fv 1 validator, possible only before fv 1 ships.
- **The gap check, exactly.** A log whose `snapThrough` is past what this device has read from that device's own files (the greater of its `logReach` and its `snapReach`, the latter only while the snapshot version it came from is the listed one, below) reads that device's snap, if its listed sha isn't joined, and joins it. If the state then still doesn't reach the `snapThrough` (a stale read, or no snap listed), the log waits: status `saving`, and the head is not recorded as handled, so the next poll lists again. A snap that a log needs and that can't be read halts that device's stream under the snap's name (`needsAttention`, or `needsUpdate` for a newer format), and the stream heals once a readable one is listed. A stale snapshot that was read is still joined: it is valid data, and joins only grow state.
- **Owner decision D24 (2026-10-12): a snapshot's coverage claims are never trusted for correctness.** A snapshot's `joined`, its `seen` and its `through` are its author's word, which no reader can check. Until D24 a reader marked every file version in a joined snapshot's `joined` map as joined, and took its `seen` into the vector that decided which log ops were already held and whether another device's log needed that device's snapshot. A validly encrypted snapshot that over-claimed either one left the devices that read it without ops that devices which kept up had, for good: replicas holding the same repo materialised differently, which guarantee 3 forbids. Now a snapshot is only a head start, for its own device's stream. On cold start, catch-up and a rehome's cold join alike, a device reads every listed log whose blob sha it has not itself joined, and joins its ops, and every listed snapshot whose blob sha it has not joined, whether a log needs it or not (the amendment below). A snapshot's `joined` map marks nothing joined, its `seen` for other devices decides nothing (it is still joined into the state's `seen`, which every own op carries as `vv`), and its `through` only closes its own device's gap, and only while that snapshot version is the listed one: it never leaves out ops of a log this device reads. So a device's state is the join of the genesis, its own ops and the files it has read itself, and `meta.joined` names only those. There is no separate cold path any more. The read of the largest listed snapshot at cold start went with D24: its only use was letting its claims skip other files. Section 8.3's "skipped through `joined`" for retired devices no longer holds: a cold start reads each retired device's log once, and its snapshot if that log names one.
- **Meta gains `logReach` and `snapReach`** (D24), per other device: the last L of the version of its log this device joined, and the `through` of the version of its snapshot this device joined. A log's ops at or below `logReach` are left out only when joining one would change nothing in the state the device holds (`holdsOp` in state.ts, the same test the join makes, without changing anything); every other op of a newly read version is joined. A log whose `snapThrough` is past both waits for its snapshot (section 8.2). Both are read only from the device's own files and saved in the transaction that joins them, so no other file can raise them. Neither is `seen`, which other snapshots raise. A snapshot's `through` sets only `snapReach`, so an over-claimed `through` can close its own log's gap but never hides that log's ops; and it counts only while that snapshot version is listed, so once overwritten it hides no later log version's ops either (below). A later version of a device's log that holds an op below the last L of the version this device read before (one inserted into a Lamport gap), or rewrites one at the same L, is that device contradicting its own history (a fork, section 10.3), and takes a key holder replacing a file: honest own Ls only grow, and a sha-conditional PUT makes a clone rehome instead of overwriting. Until the stage 5 review (2026-10-12) a reader filtered such ops by L alone, so an op the listed version inserted below `logReach` reached a cold start but never a device that had read the earlier version: two devices holding the same listed files materialised differently for good. Now such an op is joined whenever it changes the state, as a cold start joins it. The join is a semilattice, so an op that changes nothing now changes nothing after any later join, and leaving it out is the same as joining it: a reader's state is the join of the versions it read. A rewrite at the same L is then decided by the equal-tag tie-break; the op it rewrote is content found only in an overwritten version, which guarantee 3 does not promise to every device (owner decision D25, below): no writer in the app produces such a version. The cost is CPU only: at most one check per op of a newly read version (a log holds at most about 200 ops or 40 KB after trims), no request. A reach of 0 holds nothing and is never stored (stage 5 review, 2026-10-12): a snapshot at `through` 0 is valid (its `seen` for its own device is absent, which counts as 0), and every device reads every listed snapshot (below), so one planted under any device id made every reader store `snapReach` 0 for it. `checkMeta` took each reach entry as a Lamport value of at least 1, so the tab that stored it carried on and every later load of that device was `unreadable` (`malformed`), a new device too once it had joined the same snapshot, against guarantees 1 and 2. Joining such a snapshot now clears the entry, and `checkMeta` accepts a 0 entry in either reach (as a restore cut's 0 entry, it cuts nothing), so a meta that an earlier build saved that way still loads. This amends the section 10.1 meta list.
- **D24 amended: every device reads every listed snapshot, needed or not** (stage 5 review, 2026-10-12). As first built, D24 read a device's snapshot only when that device's log named a `snapThrough` past what this device had read from that device. A device that kept up never read it; a cold start, or a device offline across the compaction, always did. A snapshot's state is joined as it is, so a register value only the snapshot holds (a crafted one, or a buggy build's, like the S1 snapshot before 0fde658) reached only the devices that read it. On the fake GitHub, with three devices idle on the same head and every listed file current, one showed the snapshot's value for a record and another the record's own, for good: nothing made the device that kept up read the snapshot, since its log never changed again. So a snapshot's state, not only its coverage claims, was trusted by whichever devices happened to read it. Now every device reads every listed snapshot of another device whose listed sha it has not joined, whether a log needs it or not, so every device that has read a listing holds the same snapshot versions; joins are commutative and idempotent, so they converge. A snapshot that can't be read halts its stream only when a log needs it, so a garbage snapshot no log needs still halts nothing, and its refusal is remembered by sha, so it is read once. The one refusal that depends on the listing as well as the bytes (a `seen` naming a device with no file, below) is not remembered that way: it is checked again against every listing. Content found only in an overwritten version of a file is not closed by this rule; guarantee 3 does not promise it to devices that never joined that version (owner decision D25, below). The cost: each compaction costs every other device one snapshot GET (about 330 KB at 10 years), at most once per 200 ops or 40 KB of the compacting device's log.
- **An overwritten snapshot's `through` closes no gap** (stage 5 review, 2026-10-12). `snapReach` was the greatest `through` this device had ever joined from a device's snapshot, so one over-claimed `through`, read once, went on closing that device's later gaps after the snapshot was overwritten: a device offline across the next compaction skipped the new snapshot, joined only the log's ops above its `logReach`, and showed `idle` without the ops in between, until that device's `snapThrough` passed the forged value. Now `snapReach` is the `through` of the snapshot versions joined by the latest read that joined one (the version `joined` names), and the gap check counts it only while that version is the listed one, or was joined in the same read. So the newer snapshot is read, and if it can't be, the log waits (halted) rather than being joined across the gap. Honest flows read nothing more: an honest snapshot's sha changes only when its device compacts at a higher `through`, and every changed snapshot is read anyway (above). A stale listing that names an older snapshot lowers `snapReach` to that one's `through`, which at worst makes a log wait for, or read again, the newer one.
- **Request cost of a cold start under D24.** For an epoch whose files name N other device ids (live and retired), C of which have a snapshot listed: `verifyRepo`, 1 ref read, 1 listing, the genesis, N log blobs and C snapshot blobs, so N + C + 3 GETs after `verifyRepo`, at most 2N + 3. A rehome's cold join reads the same, its old id included. Before D24 it was the genesis, one snapshot and the logs changed since that snapshot. Bytes stay bounded because logs are trimmed after each snapshot: a log holds only the ops since its device's last compaction (under the 200-op and 40 KB trigger, apart from a log that can't compact yet, see Design questions), and a retired device's last trim usually left it empty. Each snapshot is about 330 KB at 10 years. A household with 6 device ids that all compacted reads 15 GETs and about 2 MB at 10 years. The count grows by one log, and one snapshot once it compacts, per device id the epoch has ever had; a restore's new epoch starts it again. A device that keeps up reads only files whose sha changed: a log GET per change to another device's log, and a snapshot GET (about 330 KB at 10 years) per compaction of another device, at most once per 200 ops or 40 KB of that device's log (the amendment above; before it, a device that kept up never read a snapshot). A device back from offline reads every changed log and every changed snapshot, at most N + C. A log waiting for its snapshot is not downloaded again while it waits (above), and a snapshot refused only because its `seen` names a device with no file is not downloaded again until every device it named is listed (below). `compaction.test.ts` counts these reads ("a cold start reads every listed log and snapshot once", "a reader already past K doesn't need the snapshot to join the log, but reads it once").
- **A snapshot's `seen` names only devices with a file in the epoch.** Stage 5 is the first stage where a reader takes a remote file's `seen` into its own state, and every later own op carries that whole vector as its `vv` (section 3.1), as does every own snapshot. The validator bounds a snap's `seen` only from above, for devices that hold a register, so a snap of about 70 KB naming 5,200 devices that hold nothing passed every check, and a device that joined it made ops too large to push for the rest of the epoch (`needsAttention` for good, its writes reaching no one). A reader therefore refuses, as `malformed`, a snap whose `seen` names a device, other than the snap's own, with no log or snap listed in the epoch. Every honest snapshot passes: a device's ops reach another only through its log, nothing is ever deleted, and a listing is one commit's tree, so every device an honest snapshot has seen has a file in any listing that holds it. The refusal halts the snap's stream (section 12) when a log needs that snapshot; one no log needs halts nothing. A cut listing (`truncated`) proves no absence, so there the check is skipped. Unlike every other refusal, this one depends on the listing, not only on the file's name and bytes, so it is not remembered as final (stage 5 review, 2026-10-12). As first built it was kept with the others by name and sha: once a device the snapshot named was listed, a cold start joined the snapshot while a tab that had refused it went on refusing it from memory, both idle on the same head, and a reload did not help because that head was already handled. Now the tab keeps, by name and sha, only the devices the snapshot named with no file, checks them against every listing without downloading the snapshot, and downloads and checks it whole once all of them are listed. The head is still recorded as handled after such a refusal: every device refuses that snapshot at that listing, a device gets a file only through a commit, which is a new head every device lists and reads again, and nothing is ever deleted, so a listing that lists the device comes later in every device's view. A cut listing stays cut as files are added, so devices reading cut listings join the snapshot alike, and a device that refused it at an earlier full listing joins it at its next one. A snapshot's `joined` map was first taken only for listed names; since D24 it is never taken, so its names never reach meta or an own snapshot. This is a reader's rule against a listing, not a change to the fv 1 validator.
- **A rehome's cold join reads snapshots too** (section 10.3 step 3, which points at section 8.3). It reads the genesis, then every snapshot and every log, the old id's included, and takes no file's coverage claims (D24). The fallback to a version this device joined before now covers snapshots as well as logs. Without the snapshot, a device that had compacted would rebuild without its own ops at or below K, and re-issue them all under the new id.
- **Writers keep within half the read bounds; own files are read back within twice them.** The read bounds above (`REPO_FILE_MAX_BYTES`, `REPO_FILE_MAX_PLAIN_BYTES`) were a reader's only, so a device could publish a file every reader refuses. A snapshot is the union of everything the device joined, so files each within the bounds could add up past them; the device then trimmed its log behind a snapshot no one could read, and its trimmed ops reached no other device, a new one included. Now the own log and the own snapshot are measured before they are sent: the inflated JSON against half of `REPO_FILE_MAX_PLAIN_BYTES` (16 MiB), and the sealed text against half of `REPO_FILE_MAX_BYTES` (2 MiB, about 6 times a 10-year snapshot). Half, so a later build can raise the read bounds within fv 1 before any writer reaches them. A snapshot past them is not published and the log stays uncompacted, as for one the validator refuses; readers keep joining the log. An own log past them is never sent: the cycle still pulls, local reads and writes go on, the device shows `needsAttention`, and the reason is logged once per log content. Compaction can't help such a log, since only a confirmed log compacts (see Design questions). Reading back its own log or snapshot in step 5 (section 7) or 8.1 step 3, a device uses twice the read bounds: a size says nothing about whose history a file is, and a build whose bounds were raised may have written it, so a size-only refusal there no longer rehomes the device. Twice keeps the memory such a read can take finite, so a crafted file under the own name still can't take the tab; a file past even that is a fork as before. Such a confirmed own log is also due for compaction, not an error: the trigger in section 8.1 counts it as past the size limit, since compaction is the one way to shrink it, and the snapshot is measured on its own. One that fits is published and the log trimmed; one past the bounds too is not published, and the device stays `idle` with the log as it is. Building the log text only to measure it once let the size refusal escape the cycle, which then failed every time and showed `pending` with nothing pending. Once a ledger's state outgrows the write bounds, the remedy is a build that raises the read bounds (and so the write bounds); a restore can't help, since its genesis would be as large. The genesis is not measured here: its writers (create and restore) come with stage 6.
- **The epoch's genesis state is kept in memory**, because every snap is checked against it (codec.ts). The cycle keeps the one it reads. Otherwise the genesis is read once per tab by its blob sha, when a snap first needs checking.
- **Local compaction (section 8.4)** is queued behind the mutation that takes `tail` past 500 entries, and after a load that finds it past that. It never flags `deviceSaveFailed`, because no user write was refused. If it fails, the next mutation past the limit tries again. The limits (200 ops, 40 KB of log text, 500 tail entries) are counts and sizes, never time. They are the engine option `compaction`, which tests lower.

- **Owner decision D25 (2026-10-12): content found only in an overwritten version of a file is outside guarantee 3, and the app never produces such a version.** Guarantee 3 is that devices which have joined the same file versions materialise identically, and that the app itself never drops content from a file it overwrites. A passphrase holder who overwrites their own device's file with a version that drops content is an insider rewriting history, out of scope as forging a tag or authorship is (D21, and Trusted under the threat model below). This resolves the question the stage 5 review left open, with option (a): a device that read a version of a file keeps what it held (joins only grow), and a device that never read it can't see it once the file is overwritten, so two devices that joined different versions of one file may differ for good, each internally consistent. Option (b), making the state a function of the listed versions by checking each newly listed version against the one joined before and rebuilding from the listed files as a rehome's cold join does when it holds less (one more GET per changed file, and N + C + 3 GETs, about 2 MB at 10 years for 6 device ids, per rebuild), and option (c), reading every earlier committed version of each file at cold start (a cost that grows with the repo's history, unbounded), are rejected: both spend requests on every device to defend against someone who could already change or delete anything through the app. `compaction.test.ts` ("D25: content only in an overwritten version of a log stays with the device that read it, and a cold start never sees it") pins the accepted behaviour: a log planted with valid ops at L 2, 3 and 4 is read by r, then replaced by one holding L 2 and 4; a cold start c and r end idle on the same head, r showing three records and c two, each consistent with the versions it joined. What the app's own writers overwrite, and why each keeps every piece of content in a listed file: the own log only grows in its last L, and a trim drops only ops at or below K, which the confirmed own snapshot listed at K holds ("snapshot first, trim second", invariant S1, with the snapshot checked against every reader's validator and the write bounds before it is sent); the own snapshot is replaced only by one at a higher `through` taken from the device's state, which only grows by joins, so it holds everything the version it replaces held (a cloned profile whose chain matches at the listed snapshot's `through` may replace that snapshot with its own: it holds the same own ops through that point, and the rest of what the replaced snapshot held came from other devices' files, which still hold it); and every PUT is sha-conditional, so an instance of the device that is not this history (a cloned profile, a restored backup) rehomes under a new id instead of overwriting (section 10.3), its unsent ops re-issued there. The genesis is never overwritten: create and restore (stage 6) write a new epoch's files. A randomised run on the fake GitHub during the D25 review (300 seeds of two to six devices: adds, edits, deletes, compaction every 2-4 ops, cloned profiles that rehome, lost PUT responses and stale reads; about 1,660 snapshot PUTs, 3,080 log PUTs past a trim and 1,280 device ids) found every committed version of every file held by the files listed at the head, and a cold start equal to every device that kept up.

Design questions left open by stage 5's review (the conservative reading is what is built):
- **An own log past the write bounds before its first push has no way out.** Section 8.1 compacts only a confirmed log, and K moves only through a confirmed snapshot, so a device whose unpushed ops alone pass 2 MiB (one entry with megabytes of text, or years of edits made offline) can neither push nor compact. It shows `needsAttention` for good and its ops stay local, which is safer than publishing a file every reader refuses. Ways out would be pushing a prefix of the log, or a snapshot taken through an unconfirmed log, which needs the readers' gap check to fetch a snap whose author's log ends below it. Neither is in the spec.
- **`seen`, and so every own op's `vv`, still grows by one entry per device with a file in the epoch.** The rule above makes each entry cost a listed file, as a log always did, but tens of thousands of device files (a git tree lists up to 100,000) would still make every own op too large to push. A deletion's `vv` in another device's log is also joined as it is and copied into every own snapshot, so a log whose deletions carry a huge `vv` can keep this device's snapshots past the write bounds and its log uncompacted. Both take a key holder's crafted files, and neither loses data, but both end in `needsAttention` once the own log passes the write bounds. Refusing a log whose op `vv` names an unlisted device would close the second, at the risk of halting an honest log's stream if the honesty argument above had a gap, so it is not done. Bounding both needs `vv` to carry only the entries the fence, the restore cut (stage 6) and the notice rule (stage 7) read, which changes what an op holds; it is left to those stages' design.
- **`idle` while K is past `ownLogK`.** Between a confirmed snapshot and its trim the status is `idle` with nothing pending. With the snapshot rule above that window loses nothing for any reader, so it is left as it is.

Restore epochs, create, join, forget and export, settled while building stage 6 (spec section 9; `SyncEngine.ts`, `leftBehind.ts`, `ledgerRepo.ts`):
- **A newer epoch is switched to, not halted on.** The stage 4 placeholder is gone. When a full listing's winner (section 9.1, with the counted-run rule above) is newer than the device's epoch, the cycle reads its genesis with the validator every reader runs, takes a write turn (as a rehome does, so no write is diffed across the change), and in one transaction moves the old state into `old`, stores the groups left behind, and starts the new epoch from its genesis under a new device id, its first log carrying `prev: {epoch, device}` (section 9.3 steps 1 to 3). The same cycle then reads the new epoch's files from the same listing (step 4). Nothing more is read from or pushed to the old epoch: unpushed own ops stay in the old state, and are offered (below). A cut listing still never switches (stage 4).
- **A newer genesis that can't be read keeps the device where it is** (section 9.1): `needsUpdate` for a newer format, `needsPassphrase` for one the key can't open (undecryptable, or another salt and iterations), and `needsAttention` for a malformed one, which section 9.1 doesn't name. The cycle stops before the push, so nothing more is sent to the old epoch, but local writes are not refused (unlike a newer format on the device's own epoch's genesis, stage 4): they are the device's own changes, offered once it can switch. A newer genesis this device can't open is named (owner decision D26, below): a malformed or undecryptable one the app never writes, and deleting it resumes sync; one under another key may be another device's create that raced this one (or a ledger under a changed passphrase), and deleting it removes that ledger; and one whose epoch another device already joined is restored to its previous version, never deleted (the fourth review, below).
  - *Stage 6 second review (2026-10-12), superseded by D26 (below).* One such genesis stopped sync for good, against guarantee 2: no device could switch to it, and every restore was refused while a newer winner was listed (the stage 6 review's fix (4) below), so nothing could ever be listed after it, and createLedger answered `exists`. The review numbered a restore after a newer winner this device can't open (`nextEpochKey(winner)`, still based on the device's own epoch), so that devices stuck behind it would switch to the restore. D26 removed that rule: such a genesis is recovered by deleting the file the device names.
- **Owner decision D26 (2026-10-12): a genesis no device can open is recovered by hand, never restored past.** The app never writes a malformed or undecryptable one: create and restore check every genesis with the validator every reader runs and seal it with the household's key, so one appears only through an edit outside the app (a git client, a manual edit, a bad commit). One under another salt (`foreignKey`) the app can write: a create that raced this device's under its own new salt (design questions, below), or a ledger under a changed passphrase. (Corrected by the fourth review: this sentence first said the app never writes any of them.) The automatic rule the second review added, numbering a restore after such a winner (in `#writeRestore`, and so at Lamport exhaustion in `#renumber`, and in `createLedger({reason: "restore"})`'s damaged-winner path), kept producing new high-severity bugs. Restoring past a damaged winner could lose a change held by a readable epoch below it. A gap could leave a restorer told `replaced` by an unopenable file. And the two-salt racing-create window could flip-flop, each device restoring past the other's genesis. The rule is removed from all three. A newer listed genesis this device can't open is refused, as a readable newer winner is, and the engine stops safely and loses nothing:
  - the cycle pulls and pushes nothing (`needsAttention` for a malformed genesis, `needsPassphrase` for an undecryptable or foreign-key one, as before), and local writes go on. The one exception is Lamport exhaustion: the write that needs a new epoch is refused with a 503 whose message names the file, since renumbering needs a new epoch and none is written past the file;
  - `EngineState.damagedFile` names the file: `{path: "ledger/<epoch>.genesis.enc", epoch, reason}`, with `reason` one of `malformed`, `undecryptable` (it names the household's salt and iterations and still doesn't decrypt), `foreignKey` (it is sealed under another salt) or, since the fourth review, `joined` (whatever is wrong with it, a device file of its epoch is listed: restore it, don't delete it). `restore` answers `failed` with the same `damagedFile` and writes nothing;
  - `findLedger` and `createLedger` report the same. `findLedger` has no key, so it names a genesis whose header doesn't parse or that is too large (`malformed` with `damagedFile`). `openGenesis` names one that decrypts but isn't a genesis; a key derived from the file's own salt can't tell an altered body from a wrong passphrase, so that stays `wrongPassphrase`. `createLedger` answers `exists` with `damagedFile`: a restore's key is the household's, so it names every kind, while a create's key is new, so a genesis under another salt is a ledger to join;
  - `damagedFileMessage` gives the text: which file can't be opened and why, that the app never writes such a file, and that deleting it on GitHub (the repo, then the `ledger/` folder, then the file, then delete) resumes sync with nothing on the device lost. For `foreignKey` it says instead that the file may be another device's ledger created at the same time, or that the household passphrase changed, and that deleting it removes that ledger (it never says Ledger never writes such a file); for `joined`, not to delete it and how to restore its previous version (fourth review, below), or, for a joined genesis whose `cause` is `foreignKey`, to join that ledger with its passphrase (final review, below).
  Once the file is deleted, the next listing doesn't count it. The cycle finds this device's epoch winning again, clears `damagedFile`, joins and pushes as before, and the ops the device kept while stuck go out. Or, when another genesis of the same number is listed, the counted run still counts that number, and the device switches to the greatest remaining key. A winner named by the cycle, by a restore's refusal or by its step 6 is the greatest counted key, so no counted epoch lies above it. A genesis named by a gap check (a restore's, or `createLedger`'s epoch 1) is not the greatest counted key: it counts for nothing in the listing, since its number lies past a gap. Design questions left open by stage 6 (the conservative reading is what is built):
- **Other devices' leftovers are only what this device had joined.** A log PUT that lands in the old epoch after the genesis is offered on its own device (AC13) but on no device that switched before reading it, since a switch reads nothing more from the old epoch (section 9.3 step 2: "the local old-epoch state"). Reading the old epoch's remaining logs once at the switch would widen the collapsed list at the cost of reads; D18 is met without it.
- **A device rehomed within the old epoch** lists its pre-rehome id's leftovers as another device's group: `own` is the device id at the switch.
- **Racing creates with two salts still leave a window** (stage 6 review; corrected by the fourth review). A create whose second listing ran before the other device's genesis landed is told `created`; if the other key is greater, that device stops on `needsPassphrase` with `damagedFile` naming the winner, its writes local only: `foreignKey` while the other creator has no file in its epoch, `joined` once it has written there. Deleting a `foreignKey` winner removes that ledger and resumes this one. The other creator's epoch then no longer counts, so it doesn't stop on this one's genesis (an older winner is never switched to): it reports `epochGone`, its writes local and its restores refused, and joins the remaining ledger with that ledger's passphrase (#8). Neither device writes an epoch past the other's genesis (D26 refuses a newer winner, `epochGone` an older one), so the two can't flip-flop. Once both have written, neither genesis is named to delete (`joined`), and the person joins one device to the other's ledger by hand; since the stage 6 final review a `joined` genesis keeps its `cause`, and a joined `foreignKey` one has its own text (another device's ledger, already in use under a different passphrase: join it with that passphrase), so no previous version that doesn't exist is suggested. A device whose epoch is gone never names the remaining household's later restore, which it can't open, as one to delete or roll back (final review, finding 1). The listing after the PUT narrows the window to the two creates landing within one listing's time of each other; closing it needs the engine to move to a newer epoch under another salt (derive the key for the winner's header, re-seal the local records, then switch), which is not built. A fixed epoch-1 name, so the second create's PUT fails, would close it, but a device still holding a deleted repo's state would then take a recreated repo's epoch for its own and join a stranger's genesis into its state, so it is not done.
- **A restore whose genesis landed leaves its tab refusing writes until the reload.** That is what section 9.2 step 7 asks the caller to do at once; a caller that doesn't reload leaves the tab read-only (its cycle still switches it in place), which is not a permanent block, since a reload ends it.

The second review restored past a newer winner the engine couldn't open, and past a damaged one in `createLedger`; D26 removed both. The cycle reads it again because its sha changed, finds it can't be opened, and stops with `needsAttention`, local writes going on, as before D26. Deleting it would leave the device's epoch uncounted, so `damagedFile` names only a newer winner. The app never overwrites a genesis (D25), so only an edit outside the app does this.

A create must set every field (the validator's whole-create rule, section 12.1), so the other fields can only come from the group's snapshot, which is what happens. Notices, the left-behind UI and the status surface, settled while building stage 7 (spec sections 4, 4.1, 4.2, 11 and 12; `notices.ts`, `noticeActions.ts`, `SyncEngine.ts`, `client/src/githubStorage/sync/`):

Section 4.2 rule 1 carries the value-difference condition: R's value must differ from M's, so "edit / edit, same field, same value" tells no one, as section 4's table says.
- **An EMI's balance pair notifies even when both pairs are equal.** Two devices recording the same instalment from the same state write the same `remainingAsOf` and `asOfDate`, and one payment is kept (payments are state, not increments); with the value-difference condition alone the losing payment was silent. Owner decision D20 tells the loser with "Record again", so the pair (one notice for both registers, as stage 1's amendment asks) notifies whatever its values. Every other register needs a value that differs. This is the conservative reading where two rows of section 4's table meet (same value, and payEmi / payEmi): an extra notice is dismissed in one tap, a payment folded into another is lost without a word.
- **A snapshot stands in for vv only for its own device's writes.** Section 4.2 says the snapshot's `seen` stands in for R.vv when R arrives in a snapshot. That holds for the snapshot of R's own device: `seen` only grows, so its `seen[me]` is at least R.vv[me], and the notice can only be missed (section 12.2 item 6). Another device's snapshot that carries R says nothing about what R's writer had seen: a device that joined R without ever seeing M has `seen[me]` 0, and a causally later change was told as a clash, against AC7. The engine passes each snapshot with its device, and only that device's writes take its `seen` (the least of them, when two versions arrive at once). Usually R also arrives through its own device's log or snapshot, since every listed log and snapshot is read (D24), and is told then; the stage 7 review (below, finding 11) records when it isn't. This amends section 4.2.
- **Notices are worked out per join, against its result.** The engine joins everything one cycle read (the ops of every log and every snapshot, and a genesis it hasn't joined) as one delta, and works out the notices from the state before it and the register that wins the whole delta. A write that would replace mine but is itself replaced in the same delta by a write that had seen mine tells nothing, where joining them one at a time would have told of the first. The notices are stored in the join's own transaction, so a reload never loses one whose join was saved.
- **Who rule 1 skips, and how rule 2 finds my op.** Rule 1 skips a register of a record the same join leaves deleted (rule 2 tells that, or nothing when the delete had seen my edit) and the `cat` register (only a genesis sets it). Rule 2 looks for my content op among the record's registers as they stand before the join: the greatest L of a register tagged with my id, other than `_c`, `_s` and `sortKey`, above the deletion's `vv[me]`. A content write of mine that another device's write had already replaced is not found there; if that write was concurrent, rule 1 told it.
- **Stored notices.** A notice a join raises is keyed by (winner op, loser op, kind, what it is about), `"<L>.<device>/<L>.<device>/<overwrite|deleted>/<record or unit key>"` (stage 7 review finding 4: the pair alone dropped one of two notices one remote op raised); a fence notice by (winner op, loser op), `"<L>.<device>/<L>.<device>"`; and the rehome notice by `rehome/<new id>`. One this build can't read (it doesn't decrypt or isn't a notice this build writes: damaged, or a newer build's) is kept in the store byte for byte, left out of memory and the UI, and logged, and the device loads as usual (owner decision D31, below); a notice told later under its key never writes over it. A left-behind group this build can't read still leaves the device `unreadable` (`malformed`): it holds changes. The clone is DocumentBackend's (`structuredClone` of the whole document, about 33 ms), which AC1 keeps unchanged. A phone 3 to 5 times slower would take 300 to 450 ms a write.
  - *Every commit re-checks and re-seals the whole own log* (`#pushSoon` builds the keepalive text): a few ms a write, bounded by the 200-op compaction point.
  - *The chain store grows without bound* (above): one sealed entry per own op, about 205 bytes each.
  - *The snapshot is 2.4 times the design's estimate* and 40% of the write bound at 10 years; a ledger about 25 years old at this rate would reach the bound, and its log would then go uncompacted (`#ownSnapText` refuses a snapshot past the bounds), and nothing would be lost.

**Stage 8c-2 (phone speed, 2026-10-14).** The owner chose to fix stage 8c's two deferred phone costs before the real-GitHub smoke test. No change to the on-disk format, the op format, the sealed log format or the wire protocol, and the #5 parity suite is unchanged.
- **The join hands over the genesis it has opened.** `initialize(epochKey, state, genesis?)` takes the genesis #8's join has just read (its blob sha and state) and records it as joined, and as the state snapshots are checked against, as the first cycle's own read would have. Without it nothing changes, and a genesis replaced since has another sha, so the cycle still reads that one. This removes one request (630 KB at 10 years).
- **Blobs are read 4 at a time** (`blobReads.ts`, design section 7). `#readStreams` plans the downloads it is sure to make, in the order it makes them, and `BlobReads` starts them ahead with at most 4 in flight. Each download is handed over only at its turn, so every join, halt, refusal, gap and epoch decision is taken in the same order on the same bytes, whichever answer arrives first. A failed read stops every planned read after it, and a read that wasn't planned (a later version, a snapshot a gap asks for again) is made when asked for, so no request is made that reading one by one wouldn't make. This is pinned by `coldStart.test.ts`: the same files are joined to the same result when the reads finish out of order, and each malformed or too-new stream still halts only itself.
- **A write copies only what it reads** (`draft.ts`). `HostWrite` gains an optional `draft(doc)`, the same kind of optional host hook as stage 3's `begin()` and `ready`. DocumentBackend uses it when the handle offers one; any other host (the parity suite's, the test hosts) still gets the whole `structuredClone`. The engine's draft reads exactly as the clone would, key order included, but copies each top-level part, and each month of a month map, the first time the write reads it.
  - **Isolation.** Nothing the write can reach is shared with `current()`. `settleDraft` gives the diff a plain document whose unread parts are `current()`'s own objects. The engine then discards it: the committed document is `rematerialize`d from the previous one, which copies what changed and never edits in place. `writeIsolation.test.ts` pins that every value a call returns is the caller's own, that a write never changes a document handed out before it, and that a refused write leaves `current()` the same object.
- **The diff passes over shared months.** A month the settled draft shares with `current()` (the very same list) holds current's own records unchanged. It contributes nothing to the op and isn't walked, but an id it lists that another month also lists is still refused, at the same record. `diff.test.ts` compares shared and copied documents on random writes and on every fail-closed case.
- **Measured** with the stage 8c run (`LEDGER_PERF=1`), old and new engine run side by side so both saw the same machine load (an earlier back-to-back pair was distorted by another process's test run):

- **What a run does, all through the real engine and `DocumentBackend`:**

  5. writes past a lowered compaction point (6 ops) write a snapshot, and a third device cold-starts from the snapshots and logs on GitHub and converges.

Stage 8 (#8 join, create and onboarding) acceptance requirements that stage 6 set:
- **STAGE-8: joining from `epochGone` offers this device's own changes first** (stage 6 final review, finding 8). `epochGone` (with `EPOCH_GONE` and `EPOCH_GONE_EMPTY`) promises that this device's changes are kept on it, but the join #8 offers replaces its sync state. Before that join clears anything, #8 must offer the device's own changes: an export of its current document (`exportBackup`), or carrying them into the joined ledger as an own left-behind group with the cut `{}` (as a switch does), shown prominently (D18). It refuses, unless the person chooses to drop them, as `forgetThisDevice` does for unsynced changes. With no winner (`EPOCH_GONE_EMPTY`), the way on is a restore of this device's export into the empty repo (`createLedger` with reason `restore`), or a new ledger.
  - **Met in #8 part 4 (2026-10-14; owner decisions D34 and D35).** `SyncEngine.rejoin()` is the join, asked by the person from the bar (`EpochGonePanel`); the cycle still never moves a device off a gone epoch on its own, since a listing that doesn't count it may only be stale. On a fresh, full listing it reads the winner's genesis with the device key and switches as a restore's switch does (`#switchToListed`, so `#adoptEpoch`), the gone epoch projected with the cut `{}`: everything the device held there that the winner doesn't is left behind, its own changes as its own group, shown first (D18), and Re-apply brings them in. Nothing is dropped. **D34:** the changes are carried over, not exported first. **D35:** a winner under another passphrase's salt (`foreignKey`: a racing create's, or a changed passphrase) can't be joined this way, because this device's records are sealed with its own key; `rejoin` answers `otherKey` and changes nothing, and the panel offers a backup of this device (`exportBackup`, under its own passphrase) and then Forget and join. With no ledger left, the panel's "Create a new ledger from this device" writes a genesis of what the device shows (`createLedger`, reason `restore`) and rejoins it. `rejoin` also answers `notGone`, `empty`, `unknown` (a cut listing, or a switch got there first), `needsUpdate` and `damaged`. An own edit of a record another device created on the gone epoch is skipped until that device's group, also offered, brings the record back (section 9.4).
  - **Review of part 4 and owner decision D36 (2026-10-14): offer everything.** The first version reused the restore switch's filters, which judge what the winner "holds" by its genesis. A restore's genesis is close to its state, but a rejoin's winner is usually a long-lived ledger whose genesis is far behind its logs, so own changes were dropped: a delete of a record the winner got from a log (S1), and an unlock matching the genesis but not the winner now (S4). An earlier own group could also be lost on a later switch (S5), a create from the device that lost a race lost everything (S7), and going back into an epoch this device used before re-offered its old history there as its changes, whose Re-apply could set back newer edits (S3). The owner chose to offer everything rather than read the winner whole first (D36). So:
    - a rejoin projects the gone epoch with `leftBehind(…, { all: true })`: every register and delete above the cut `{}`, whether the winner's genesis holds it or not, since Re-apply of what's already there changes nothing;
    - groups shown are carried as they are, with no `withoutHeld`, and no kept epoch is projected again (`NewEpoch.rejoin`);
    - on every switch, a projection never replaces this device's own group under the same marker, its former device id after a revisit, with another device's;
    - "Create a new ledger from this device" bases the new genesis on the gone epoch (`createLedger`'s `basedOn`), so a later switch to a racing create's winner projects that epoch again and offers the changes;
    - `rejoin` requires the cycle to have said the epoch is gone (`epochGone`): one listing may be stale (S6);
    - a rejoin's switch no longer relabels a running cycle (`#cycleFor`);
    - an unreadable winner is not named as a file to delete.

    The six regressions (S1, S3, S4, S5, S6 and S7) are tests in `rejoin.test.ts` that fail without these changes. ## Threat model
Owner decision, 2026-10-10.
- **Trusted: household members.** Encryption keeps outsiders out. Anyone who can produce a validly encrypted file holds the passphrase, and could already change or delete anything through the app. So a key holder forging a tag, a device id or authorship, rewriting another device's edits, or overwriting a device's file (their own included) with a version that drops content it held (owner decision D25), is out of scope and not a bug.
- **Guaranteed: no repo file, however corrupt or crafted, may**
  1. crash the app or throw uncaught;
  2. lose a committed local change, or make any later legitimate local read or write fail (a 500) or block permanently. A damaged **newer** genesis (newer than the device's epoch) written outside the app stops sync, safely and with nothing lost, until the user deletes the file the app names, or restores its previous version when another device already joined its epoch (owner decision D26). The exceptions: an overwritten genesis of the device's own epoch is never named, since deleting it would leave that epoch uncounted, and sync stops until its previous version is back (design questions, stage 6); and a device whose epoch is gone (`epochGone`: its genesis, or one below it, was deleted on GitHub, perhaps on another device's word that it was a racing create's) can't sync again in that epoch. Its local writes go on and its changes stay on the device, but it rejoins only through #8's join, which must offer those changes first (STAGE-8, above; stage 6 final review);
  3. break convergence: devices that have joined the same file versions must materialise identically, and the app itself never drops content from a file it overwrites (owner decision D25). Content found only in a version a key holder overwrote reaches the devices that joined that version and no other; each stays internally consistent.
- **A snapshot is only a head start** (owner decision D24, 2026-10-12). Devices never trust a snapshot's coverage claims (`seen`, `joined`, `through`) for correctness. On cold start, catch-up and a rehome's cold join, a device still reads every listed log and every listed snapshot whose blob sha it has not already joined itself (a snapshot whether a log needs it or not, so a value only a snapshot holds reaches every device alike), joins every op of a log it reads that would change its state (none is left out by L alone), decides a refusal that depends on the listing against each listing afresh, and lets a snapshot's `through` close its device's gap only while that version is the listed one, so no file, however corrupt or crafted (one that over-claims coverage included), can break convergence through its claims. The cost is recorded under stage 5 above.
- **Never refused: legitimate flows.** Create, join, rehome after a fork, restore to a new epoch, re-apply (spec section 9.4) and snapshots. Every file they write must pass the validator.

The design meets this through the spec's section 3.6 and section 12, and D24: a device holds a file only once it has read and joined it, never on another file's word, and its state is the join of the genesis, its own ops and the files it holds; each file is validated whole before any join, a malformed file halts only its own stream (`needsAttention`) and is never partly applied, the cycle's catch-all keeps status from sticking, and the tag order is total even on malformed history. A halted stream is not a block under 2, because local reads and writes carry on. Nor is a damaged newer genesis (D26): local reads and writes carry on (only a write that needs a new epoch at Lamport exhaustion waits), the device names the file, and deleting it (or, when another device joined its epoch, restoring its previous version) resumes sync. The rules above that keep a remote value from making a later local op fail (order key and `sortKey` shapes, `st/timeZone`, calendar dates, the payment bound), and the new epoch at Lamport exhaustion, are what 2 needs.

Some rules above, such as binding a snap to its genesis's registers and to its own `seen`, mainly stop a key holder rewriting other devices' values, which this model puts out of scope. They stay as written: fv 1 is unreleased, and within one `fv` a rule may later be loosened but never tightened, so strict is the conservative choice. Loosening any of them later must keep guarantees 1-3 and the never-refused flows.

## Alternatives considered
- **Keep the shared file and fix the merge:** every fix on the old branch tried this, and each fix created new bugs.
- **A CRDT library (Automerge, Yjs):** it adds a large dependency to the GitHub bundle. Its opaque binary history would sit inside our encryption, and it still needs our own rules for deletes, restores and one-writer files.
- **Edit wins over delete:** this needs a resurrection rule that depends on timestamps, which caused the earlier B2, B3 and B25 bugs. Remove-wins keeps the edit recoverable as "Add it back as a new entry".

## Consequences
- Convergence rests on one tested property: the join is commutative, associative and idempotent. `client/src/backend/sync/` holds the pure core and its law and convergence tests, and nothing in the app imports it yet.
- The repo grows by about 60-80 MB a year per active device, and nothing is pruned. A "start a fresh repo" procedure goes into `docs/DEPLOY-github.md` (#11).
- Two offline payments on one EMI keep one result (payments are state, not increments). Locks are not enforced across offline concurrency. Per-field merge can combine two people's edits to one expense.
- A future write path that the diff can't represent fails in tests, so it can't silently lose data. Adding one means extending the op format under a new `fv`.
